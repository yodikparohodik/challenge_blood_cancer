# OpenSpec: Правило разработки задач

## 📋 Обзор правила

**Название**: OpenSpec Development Workflow Rule
**Версия**: 1.0.0
**Статус**: Active
**Дата вступления в силу**: 2024-01-15
**Обязательность**: Обязательно для всех новых задач

---

## 🎯 Цель правила

Все новые задачи в проекте SelfLearn должны оформляться и вестись строго по процессу **Plan-Implement-Verify-Document-Archive (PIVDA)** с использованием формата спецификации OpenSpec.

---

## 🔄 Процесс PIVDA

### 1️⃣ PLAN (Планирование)

**Цель**: Четкое понимание задачи до начала реализации

**Требования**:
- [ ] Создать файл спецификации в `/workspace/project/specs/`
- [ ] Заполнить разделы "Обзор", "Цели и мотивация", "Архитектура"
- [ ] Определить критерии успеха
- [ ] Составить план работ с этапами
- [ ] Установить таймлайн
- [ ] Получить approval от ответственного

**Артефакты**:
- Файл спецификации: `specs/SPC-XXX-description.md`
- Статус: `Draft` → `Approved`

---

### 2️⃣ IMPLEMENT (Реализация)

**Цель**: Качественная реализация согласно плану

**Требования**:
- [ ] Следовать плану из спецификации
- [ ] Писать код с соблюдением стандартов проекта
- [ ] Создавать unit тесты для нового функционала
- [ ] Документировать изменения в коде (docstrings, comments)
- [ ] Обновлять конфигурационные файлы при необходимости
- [ ] Фиксировать отклонения от плана в спецификации

**Артефакты**:
- Исходный код в `/workspace/project/src/`
- Тесты в `/workspace/project/tests/`
- Конфигурации в `/workspace/project/config/`
- Статус: `In Progress`

---

### 3️⃣ VERIFY (Проверка)

**Цель**: Гарантия качества и соответствия требованиям

**Требования**:
- [ ] Все unit тесты проходят (`pytest tests/`)
- [ ] Integration тесты проходят
- [ ] Код проходит code review
- [ ] Проверка на соответствие критериям приемки
- [ ] Проверка метрик успеха
- [ ] Тестирование в изолированном окружении

**Артефакты**:
- Отчет о тестировании в спецификации
- Логи тестов
- Статус: `Verified`

---

### 4️⃣ DOCUMENT (Документирование)

**Цель**: Полная документация для пользователей и разработчиков

**Требования**:
- [ ] Обновлен README.md
- [ ] API документация актуальна
- [ ] Пользовательская документация в `/workspace/project/docs/`
- [ ] Changelog обновлен
- [ ] Примеры использования добавлены
- [ ] FAQ обновлен при необходимости

**Артефакты**:
- Пользовательская документация в `docs/`
- Обновленная техническая документация
- Статус: `Documented`

---

### 5️⃣ ARCHIVE (Архивирование)

**Цель**: Сохранение знаний и извлеченных уроков

**Требования**:
- [ ] Заполнен раздел "Итоги" в спецификации
- [ ] Описаны извлеченные уроки
- [ ] Указаны связанные артефакты (PR, issues)
- [ ] История версий спецификации обновлена
- [ ] Спецификация перемещена в архив или помечена как завершенная

**Артефакты**:
- Завершенная спецификация
- Статус: `Archived` или `Completed`

---

## 📁 Структура файлов спецификаций

```
/workspace/project/specs/
├── template.md                    # Шаблон спецификации
├── SPC-001-feature-name.md        # Активные спецификации
├── SPC-002-another-feature.md
├── archive/
│   ├── SPC-000-old-feature.md     # Завершенные спецификации
│   └── ...
└── roadmap.md                     # Дорожная карта проекта
```

### Naming Convention

Формат имени файла: `SPC-XXX-short-description.md`

Где:
- `SPC` - префикс Specification
- `XXX` - порядковый номер (001, 002, ...)
- `short-description` - краткое описание в kebab-case

Примеры:
- `SPC-001-user-authentication.md`
- `SPC-002-api-rate-limiting.md`
- `SPC-003-database-migration.md`

## 📊 Статусы спецификации

| Статус | Описание | Можно ли начинать реализацию? |
|--------|----------|------------------------------|
| `Draft` | Черновик, обсуждение | ❌ Нет |
| `Review` | На проверке у ответственных | ❌ Нет |
| `Approved` | Утверждена, готова к работе | ✅ Да |
| `In Progress` | В разработке | ⏸️ В процессе |
| `Verified` | Реализовано, проверяется | 🔍 Тестирование |
| `Documented` | Задокументировано | 📚 Готово к релизу |
| `Completed` | Полностью завершено | ✅ Закрыто |
| `Archived` | В архиве | 🗄️ Историческая |

## 🎭 Роли и ответственности

### Автор спецификации
- Создание черновика спецификации
- Заполнение раздела PLAN
- Координация реализации
- Заполнение итогов в ARCHIVE

### Реализатор (Developer)
- Следование плану из спецификации
- Написание кода и тестов
- Обновление раздела IMPLEMENT
- Прохождение VERIFY

### Ревьюер
- Проверка соответствия кода стандартам
- Проверка полноты тестов
- Approval перед переходом в VERIFY

### Технический писатель (может быть автор)
- Создание пользовательской документации
- Обновление README и руководств
- Заполнение раздела DOCUMENT

## ✅ Чеклист готовности задачи

Перед переходом к следующему этапу проверить:

### Plan → Implement
- [ ] Спецификация утверждена (статус `Approved`)
- [ ] Критерии успеха четко определены
- [ ] План реалистичен и оценен по времени

### Implement → Verify
- [ ] Весь код написан
- [ ] Unit тесты написаны и проходят локально
- [ ] Код закоммичен в ветку

### Verify → Document
- [ ] Все тесты проходят в CI/CD
- [ ] Code review выполнено и замечания устранены
- [ ] Критерии приемки достигнуты

### Document → Archive
- [ ] Пользовательская документация готова
- [ ] API документация обновлена
- [ ] Changelog обновлен
- [ ] Извлеченные уроки записаны

---

## 🚫 Нарушения процесса

### Критические нарушения (блокирующие)
- Начало реализации без статуса `Approved`
- Пропуск этапа VERIFY
- Отсутствие user documentation для пользовательских функций

### Предупреждения
- Неполное заполнение спецификации
- Отсутствие извлеченных уроков
- Несвоевременное обновление статусов

---

## 📈 Метрики процесса

### Для отслеживания эффективности
- **Cycle Time**: Среднее время от Approved до Completed
- **Rework Rate**: Процент задач, возвращенных с VERIFY на IMPLEMENT
- **Documentation Coverage**: % задач с полной документацией

### Целевые значения
- Cycle Time: < 5 дней для мелких задач
- Rework Rate: < 10%
- Documentation Coverage: 100%

## 🔗 Интеграция с инструментами

### Git
- Ветка для задачи: `feature/SPC-XXX-short-description`
- Коммиты: `[SPC-XXX] Description of change`
- Pull Request: Ссылка на спецификацию в описании

### Issue Tracker (если используется)
- Создать issue с ссылкой на спецификацию
- Обновлять статус issue вместе со статусом спецификации

### CI/CD
- Автоматический запуск тестов при PR
- Проверка наличия документации
- Валидация структуры спецификации
